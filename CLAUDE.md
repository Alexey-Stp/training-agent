# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Triathlon coach Telegram bot. It is an npm-workspaces monorepo (Node 20+, TypeScript strict, CommonJS). The data flow is:

```
Telegram → apps/bot (grammY) → BullMQ "commands" queue (Redis) → apps/worker → Postgres (Prisma) → Telegram reply
```

## Commands

```bash
npm install
npm run db:generate          # Prisma client generation. Needed before typecheck/build/test (CI does this first)
npm run build                # builds @triathlon/core first, then all workspaces (apps import core from dist/)
npm run typecheck
npm run lint                 # ESLint on all .ts (tests and test/ dirs are ignored by lint)
npm run format:check
npm test                     # vitest run in every workspace that has tests (core, integrations-icu, bot, worker)
npm run ci                   # lint + typecheck + test + build

# Single package / single test
npm -w @triathlon/core run test
npm -w @triathlon/integrations-icu run test -- test/client.test.ts
npm -w @triathlon/core run test -- -t "NoHardHard"   # filter by test name
npm run test:watch                                    # core in watch mode

# Local dev
docker compose up postgres redis
npm run db:push              # sync schema (use db:migrate for a migration)
npm run db:seed              # demo athlete with 30 days of data (scripts/seed-demo.ts); db:verify checks a migrated and seeded DB
npm run dev:bot              # tsx watch
npm run dev:worker
docker compose up --build    # full stack
```

The Prisma config is in `prisma.config.ts` (Prisma 7) and loads `DATABASE_URL` from `.env` through dotenv. Copy `.env.example` to `.env`. Its default hostnames (`postgres`, `redis`) are Docker service names, so change them to `localhost` when you run the apps outside Docker.

## Architecture

- **apps/bot**: A thin gateway. `parser.ts` parses text into `{commandName, args}`. `index.ts` enqueues a `CommandJob` via `queue.ts` `enqueueCommand` (3 attempts, exponential backoff) and reacts 👀. It has no DB access. The only logic it holds is the `/connect icu` dialog (`connect-dialog.ts`, state in Redis) and the `/season new` wizard (`season-dialog.ts`, inline buttons, `callback_query:data` handler; callback jobs use a `jobId` per tapped message so double taps enqueue once). The connect dialog encrypts the ICU API key before enqueueing a `connect_icu` job, so the plaintext never lands in the queue. Never log message text in the bot.
- **apps/worker**: Consumes the `commands` queue (concurrency 5, rate limit 10/s). It dispatches on `commandName` in `index.ts` and validates arguments inline there. Note that `validateSetFtpArgs`/`validateLogArgs` in `bot/parser.ts` are currently unused. `handlers.ts` holds the command handlers, which return reply strings. The worker sends replies itself through a grammY `Bot.api` instance.
  - **Idempotency**: `db.ts` calls `ensureUser()`, which auto-creates the user and a default profile. `checkMessageProcessed`/`markMessageProcessed` use the `ProcessedMessage` table, so retried jobs don't double-reply. Keep this pattern when you add commands.
  - When a job fails, the worker sends a generic error message and rethrows so that BullMQ retries.
  - **Activity sync**: A second queue, `icu-sync`, holds one repeatable `icu-activity-sync` job scheduler per `IcuConnection` (`sync-scheduler.ts`). Schedulers are registered on connect, removed on disconnect, and reconciled at startup. `activity-sync.ts` (injected deps, like `icu-connect.ts`) backfills 90 days, then fetches from `lastActivitySyncAt` minus an overlap. It diffs rows by `(userId, icuId)` so repeat runs write nothing, and advances the cursor in the same transaction as the rows.
  - **Wellness sync**: The same queue holds a daily `icu-wellness-sync` scheduler per connection (`wellness-sync.ts`, same pattern, cursor `lastWellnessSyncAt`). It upserts `Wellness` by `(userId, date)` and writes only `WELLNESS_DEVICE_FIELDS`. Never let sync write the check-in fields `subjectiveReadiness`/`soreness`. `/sync` (`sync-command.ts`) runs activities, then wellness, inline.
  - **Planned workout push**: `/plan` and `/plan push` store the week as `PlannedSession` rows (`plan-store.ts` `diffPlan` on `(date, slot)`; pushed sessions that leave the plan are tombstoned via `deletedAt`). `plan-push.ts` creates, updates and deletes ICU `WORKOUT` events. It stores `icuEventId` and `pushedHash` (hash of ICU's response), and adopts orphaned events by `external_id = ta-<id>` so there are no duplicates. A third per-connection scheduler, `icu-plan-reconcile` (`plan-reconcile.ts`), flags events the athlete moved, edited or deleted as `modified_externally`. Push and `/plan` never overwrite `modified_externally`/`completed`/`skipped` rows. Workout text comes from core `workout.ts` (`renderIcuWorkout`, real ICU syntax: `Main set 5x` header, then `- 3m Z4` steps).
  - **Seasons**: `/race add` (`race-command.ts`). The `/season new` wizard ends in a `season_preview` job (`season-command.ts`), which stores a `SeasonPlan` with status `draft` and replies with the block table plus buttons. `season_confirm` activates the draft through `seasonRepo.activateDraft` (one transaction). If another season is active it only replaces it when the job carries `replace`, otherwise it returns `needs_replace`. Handlers may return a `Reply` (`reply.ts`: HTML + inline keyboard) instead of a string. Command names and callback data are shared via core `season-wizard.ts`.
  - **Rolling publisher**: A fourth per-connection scheduler, `season-rolling-publish` (`season-publish.ts`), expands the active season for local T+1..T+`SEASON_PUBLISH_WINDOW_DAYS` (T from `Profile.timezone`) with core `seasonDraftsForRange`. It then runs `materializeRange` + `pushPlannedSessions(from T+1)`. Never read or write days ≤ T. `/plan` uses the same season drafts for covered days (`plan-source.ts` `planWeek`), so the two never fight.
  - **Coach chat**: the bot routes non-command text to a `coach_chat` job (`parser.ts`; names and Apply/Keep/Discuss callback data `cc:a|k|d:<decisionId>` in core `coach-chat.ts`; bot button handling in `callbacks.ts`, which drops taps older than `COACH_DECISION_TTL_HOURS`). `coach-chat-command.ts` checks the Redis daily limit (`chat-limit.ts`, a set of message ids per user and local day, `COACH_CHAT_DAILY_LIMIT`) before any LLM call, then runs ai `runCoachChat` with the daily context, the plan for today..+6 and the last 10 `CoachChatMessage` rows. A retry resends the stored reply. `coach-apply.ts` handles `coach_apply`/`coach_keep`/`coach_discuss` (expired after `COACH_DECISION_TTL_HOURS`; `CoachDecision.userAction` records the button): it re-runs the guardrails on the current plan, then `buildCoachPatches` (`coach-plan.ts`) and `coachAnswerRepo.applyDecision` (one transaction, guarded by `accepted IS NULL`), then pushes only the decision's rows. A failed push is undone by `buildRollbackPatches` + `revertDecision` (second transaction; restored rows with ICU events go back to `draft`). Discuss seeds a coach `CoachChatMessage` with the suggestion. Rows with `PlannedSession.coachDecisionId` are protected in `diffPlan`, and push keeps their tombstones.
  - **Morning brief**: a `daily-brief` queue with one cron scheduler per connection (`daily-loop/scheduler.ts`, pattern from `Profile.briefTime ?? DAILY_BRIEF_DEFAULT_TIME`, `tz` = `Profile.timezone`). It is combined with the sync scheduler on connect/disconnect and reconciled at startup. `daily-loop/pipeline.ts` `runDailyBrief` claims `DailyBriefRun` `(userId, local date)` (lease plus conditional `updateMany`), then runs wellness sync → activity sync → context → `runCoachSuggestion` (or ai `runRulesFallback` when the context build fails) → save the rendered brief (`render.ts`: readiness line from `readiness.ts`, proposed changes, Apply/Keep plan/Discuss buttons) → send. Answers to a brief edit the brief message (`RichReply.editTapped`) with the result. A failed sync means a stale note, not an error. **Check-in**: when today has no device wellness or HRV is >1 SD off its 30-day mean, the run sends a readiness/soreness check-in (`daily-loop/checkin.ts`, `ci:` callback data in core `checkin.ts`), queues a delayed continuation job (`DAILY_CHECKIN_TIMEOUT_MINUTES`) and stops as `awaiting_checkin`; `checkin_answer` (`checkin-answer.ts`, no `ProcessedMessage` check) stores the answer first-wins and promotes the continuation once both are in. A failed send rethrows, and the retry resends the stored brief without a second `CoachDecision`. Each stage logs its `ms`.
  - **Evening close-out**: an `evening-closeout` queue with one cron scheduler per connection at `Profile.closeoutTime ?? EVENING_CLOSEOUT_DEFAULT_TIME` (same factory and reconcile as the brief in `daily-loop/scheduler.ts`). `daily-loop/closeout.ts` `runEveningCloseout` claims `EveningCloseoutRun` `(userId, local date)`, runs the activity sync (a failure rethrows and writes nothing), then core `matchActivities` (same sport, minimal duration gap, one-to-one). It writes `completed`/`skipped` + `deviationPct`/`actualIntensity` and `Activity.plannedSessionId`/`closedOutAt` in one transaction (`closeoutRepo.apply`, only rows of that date). Unmatched `modified_externally` sessions keep their status. It sends a message only for a missed key session (core `isKeySession`), a deviation above `CLOSEOUT_DEVIATION_THRESHOLD_PCT`, or an unplanned activity; quiet otherwise. Unplanned activities (`closedOutAt` set, no `plannedSessionId`) feed the weekly review.
  - **Weekly stats**: a `weekly-stats` queue with one Monday cron scheduler per connection at `WEEKLY_STATS_TIME` (`weeklyCron`, same factory and reconcile in `daily-loop/scheduler.ts`). `reviews/weekly-stats.ts` `runWeeklyStats` takes the previous ISO week of the local today (or `job.isoWeek`), loads the week plus 7 lookback days through `weeklyStatsRepo.loadRange`, runs core `computeWeeklyStats` and upserts `WeeklyStats` by `(userId, isoWeek)`. The upsert is idempotent, so there is no run row or lease.
  - **Weekly review**: a `weekly-review` queue with one Sunday cron scheduler per connection at `WEEKLY_REVIEW_TIME` (`weeklyCron(time, SUNDAY)`, same factory and reconcile). `reviews/weekly-review.ts` `runWeeklyReviewJob` claims `WeeklyReviewRun` `(userId, isoWeek)` (lease, like the brief), runs the activity sync (failure → stale note), `runWeeklyStats` for the current week, then ai `runWeeklyReview` (`prompts/weekly-v1.md`, `weekly/guardrails.ts` `runWeeklyGuardrails`: daily guardrails plus the `WEEKLY_REVIEW_MAX_RAMP_PCT` ramp cap on next week's minutes; a `scale_volume` `blockAdjustment` expands to duration diffs) and sends a ≤15-line report (`weekly-review-render.ts`) with Apply next week. The decision has `origin: 'weekly'`; `coach-apply.ts` `decisionWindow` makes Apply target the ISO week after `CoachDecision.date`, and the retry resends the stored report.
  - **Block review**: a `block-review` queue with one Sunday cron scheduler per connection at `BLOCK_REVIEW_TIME` (same factory and reconcile), plus one-off `race_move` jobs from `/race move` on the active A-race (`race-command.ts`). `reviews/block-review.ts` `runBlockReviewJob` skips unless today ends a non-taper/race block (or the A-race is still the moved race), claims `BlockReviewRun` `(userId, seasonPlanId, key)` (`block:<order>` or `race:<raceId>:<date>`, lease), runs the activity sync (failure → stale note), `runWeeklyStats` for this week, reads the block's weeks with `weeklyStatsRepo.listRange`, then core `computeBlockVerdict` → `reprojectionSeed` → `reprojectSeason` (the candidate) → ai `runBlockReview` (`prompts/block-v1.md`; a race move or volume outside ±`BLOCK_REVIEW_REPROJECT_THRESHOLD_PCT` forces the proposal) → report with old-vs-new tables (`block-review-render.ts`) and Confirm/Decline (`br:c|d:<runId>`, core `block-review.ts`, bot `block-callbacks.ts`). The run stores the proposal and `SeasonPlan.updatedAt`. `block-review-apply.ts`: Decline records `keep` on the `CoachDecision` (`origin: 'block'`) and changes nothing; Confirm runs `seasonReprojectRepo.applyReprojection` (one transaction: decision accepted only while unanswered, season `updatedAt` + A-race date optimistic lock, else `stale`; then cut/replace the future `TrainingBlock` rows) and queues `season-rolling-publish`. Buttons expire after `BLOCK_REVIEW_TTL_HOURS`; `coach-apply.ts` refuses `block` decisions.
  - **Race briefs**: a `race-brief` queue with one daily cron scheduler per connection at `RACE_BRIEF_TIME` (`raceBriefRepeat`, same factory and reconcile in `daily-loop/scheduler.ts`). `races/race-brief.ts` `runRaceBriefJob` finds races at local today+7 and +1 (`raceRepo.findByDate`) and core `raceBriefKind` decides: T-1 for every priority, T-7 only for an A-race. Per (race, kind, race date) it claims `RaceBriefRun` (lease, like the weekly review), builds the sections (`race-brief-render.ts`: T-7 week overview + core `raceChecklist`; T-1 core `buildPacingPlan` from `Profile.ftp` and `runEffortRepo.listRunEfforts`, after an activity sync whose failure only adds a stale note), asks ai `runRaceBrief` (`prompts/race-brief-v1.md`) for an intro and closing line only (a reply with a digit, or an LLM failure, gives a fixed text), stores the rendered brief, then sends. A retry resends the stored brief. B/C briefs skip the swim and weather sections.
  - **Post-race**: a `post-race` queue with one daily cron scheduler per connection at `POST_RACE_TIME` (`postRaceRepeat`, same factory and reconcile in `daily-loop/scheduler.ts`). `races/post-race.ts` `runPostRaceJob` lists races from today-14 (`raceRepo.listUpcoming`). **Recovery**: `post-race-recovery.ts` `recoveryWindows` (day after the race, never before today, cut before the next race) → core `recoverySessions` (`season/race-recovery.ts`: matrix A 7/10/14, B 2–4, C 0–2 by type, rest first then Z1 every other day, tag `recovery`; `BlockGeneratorConfig.recovery`) → `toPlannedSessions` → `materializeRange` → one `pushPlannedSessions`; idempotent, protected rows kept. Core `applyRaceOverrides` applies the same block to season expansion (replaced the B day-after cap and the A optional spins; `RACE_REACH_DAYS` = 14), so the rolling publisher agrees; after an A-race the season is over and only the job writes it. **Debrief** (races 1..3 days back): claims `RaceDebrief` `(userId, raceId, raceDate)` (lease, like the race brief), syncs activities (failure → stale, never asks), core `pickRaceActivity` (race day, longest), `race-streams.ts` `fetchRaceStreams` (`IcuClient.getActivityStreams`; failure → averages only), core `computeRaceMetrics` (`race/debrief.ts`: tiers power/hr/none, NP 30 s, halves → positive/negative/even split, HR drift) against `buildPacingPlan` as of the race date, ai `runRaceDebrief` (`prompts/race-debrief-v1.md`: narrative + exactly 3 `- ` takeaways; a number not in the facts, or an LLM failure, gives `FALLBACK_DEBRIEF_TEXT`), stores the rendered text (`race-debrief-render.ts`) before sending, so a retry resends it. No activity before the deadline (end of race day + `RACE_DEBRIEF_TIMEOUT_HOURS`, athlete tz) → `release` and look again; after it → log, ask "did you race?", `markSkipped`.
  - **Job platform** (TA-51): `jobs/registry.ts` `JOB_REGISTRY` lists every job (name, queue, kind, schedule source, owner); add new jobs there. `jobs/reconcile.ts` `reconcileRegistry` runs first in `startIcuSync` and deletes schedulers (key `<job>:<userId>`) whose job is not registered in a registry queue. `observability/`: `metrics.ts` (`job_duration_seconds`, `job_completed_total`, `job_failures_total` per job and queue; `/metrics` + `/healthz` on `METRICS_PORT` through `server.ts`), `instrument.ts` `instrumentWorker` (use it for every new per-athlete worker), `failure-streak.ts` (Redis `brief:fail-streak:<user>` counts final failures only; `SET NX brief:fail-alerted:<user>` gives one `ADMIN_TELEGRAM_ID` alert per incident, a completed brief clears both), `bull-board.ts` (`BULL_BOARD_ENABLED`, loopback only).
- **apps/web** (TA-52): The athlete web dashboard. It uses Express 5 with server-rendered HTML from plain template functions (`views/`, `esc()` on every dynamic value; no client JS; strict CSP). `createApp(deps)` takes injected repos, so tests start it on an ephemeral port with in-memory fakes and `fetch` (`test/harness.ts`). Sign-in: worker `/dashboard` (`dashboard-command.ts`) signs core `signMagicLink(User.id)` and replies with a URL button (`RichReply.links`). `GET /auth?t=` runs `verifyMagicLink`, consumes `jti` once (Redis `web:link:<jti>` NX), creates a Redis session (`web:session:<id>` → `{userId, csrf}`) and redirects. `requireSession` puts the session in `res.locals`, and handlers take `userId` only from `currentSession(res)`; never accept a user id from the request. Every rejection gives a 401 "Link expired" page plus `logger.warn({tokenId, reason}, 'dashboard auth rejected')`. POST forms need `requireCsrf`. Settings (`settings/`) is the only write path: `Profile` by `userId`. A new `notifyChatId` must pass a Telegram test message first, and every save queues `profile-reschedule` (core `profile-settings.ts`, worker `profile-reschedule.ts` → `athleteSchedulers.schedule`). Config: `DASHBOARD_*`, `WEB_PORT`, `TELEGRAM_BOT_USERNAME`.
- **packages/core** (`@triathlon/core`): Shared types (`CommandJob`, `Session`, `WeekPlan`, `RulesContext`, the `Sport`/`Intensity` enums), zod env config (`getConfig()`, cached), and the plan pipeline:
  1. `generateDraftPlan(profile, startDate)` → `addOptionalSundaySwim` → `applyRules(plan, context)`.
  2. `applyRules` runs its rules in a fixed order: SwimRotation → ReadinessDownshift → NoHardHard → WeeklyLoadCap. Each rule is a pure `WeekPlan → WeekPlan` function that appends to `warnings`/`appliedRules`. A hard session is Z4/Z5 or is tagged `vo2`/`threshold` (`isHardSession`). Downgrades go through `downgradeToEasy`.
  - `season/`: `Race`/`SeasonPlan`/`TrainingBlock` types (enums mirror Prisma) and pure invariants in `validate.ts`: blocks contiguous by `order` (block ends `startDate + weeks*7 - 1`), and the block containing an A-race is type `race`, ends that week and follows a `taper`. Issues carry `blockOrders`; `assertValidSeasonPlan` throws `SeasonValidationError`. `generateSeasonPlan` (`block-generator.ts`) allocates backwards from the A-race (race ← taper ← peak ← 2× build ← base), compresses peak/build on short runways (warnings explain each step, taper and one build always kept), ramps ≤8% between load weeks from the current load, makes every 4th plan week a 60% recovery week, and splits hours by race type plus +10 pp to the weak sport in base. Every constant is in `DEFAULT_BLOCK_GENERATOR_CONFIG`. The fast-check property test asserts the ramp cap and `validateSeasonPlan` across random inputs.
  - `season/week-expander.ts`: `expandWeek(block, weekIndex, profile, { context?, targets?, races?, aRaceWeekHours? })` turns a block week into sessions. Templates are a `Record<TrainingBlockType, WeekTemplate>` (base: no Z4/Z5; build/peak: VO2 bike, threshold run and swim; taper/race: 2 `sharpening` sessions, sessions ≤75 min; recovery/transition: all easy). Roles are placed by the profile (`swimDays`, `longBikeDay`, `bikeVo2Day`; the key run never sits next to the key bike). Each sport is sized in 5-min steps (±5% total, ±10% per sport). The result is gated by `applyRules` + `checkHardRules` (rules-engine), and `violations` should be empty. Targets default to the block averages, because per-week `SeasonWeek` targets aren't stored; `seasonDraftsForRange` passes `seasonWeekTargets` (block average × `weekVolumeFactor`, so taper weeks decline).
  - `season/race-week.ts` (TA-47): `applyRaceOverrides` runs on the draft before `applyRules`, date-based so it crosses week boundaries. A-race: `RACE_WEEK_TEMPLATES[raceType]` for T-6..T-1 sized to the race block's hours (`aRaceWindow`; sharpening T-5, rest or 20′ shakeout T-3, Z3 `openers` ≤`openerMaxMin` at T-1, nothing hard after T-3; `Race.travelDate` in T-3..T-1 is rest, T-1 travel moves the opener to T-2). B-race: `miniTaperDays[raceType]` mini-taper. C-race (and B inside the A taper): the race replaces the day, or the nearest key session. The race is one `race`-tagged session (`raceSession`, `raceDurationMin`), excluded from volume and never downgraded/scaled by the rules; taper sessions are tagged `taper` (SwimRotation skips them) and taper/race weeks set `WeekPlan.phase` (WeeklyLoadCap skips them). Taper volume: `taperWeekFactorsFromRace` (0.6/0.75/0.85 counted back from the race) and `raceWeekFactor` 0.4 of peak; `isRampException` marks taper/race weeks as the ramp-cap exception. The worker loads races with `season-races.ts` `racesForRange` (`RACE_REACH_DAYS` past both ends). `/week show` (`apps/worker/src/week-command.ts`) shows today's season week and stores nothing.
  - `season/reproject.ts`: `reprojectSeason({ season, aRace, freezeThrough, seedWeeklyLoad, weeklyHoursAvailable, weakSport })` (pure). Blocks ending by `freezeThrough` (a Sunday) are copied unchanged, a block spanning it is cut to its elapsed weeks; the rest keeps its structure when the race week is unchanged, else it is re-allocated (`allocateBlockLengths`) with phases the season is past folded forward (never past peak). Volumes restart from the seed with `buildWeeklyVolumes(..., firstIndex)` so the recovery cadence continues; the shared week sizing is in `season-weeks.ts`. Never changes a day ≤ `freezeThrough`; a fast-check property asserts it.
  - `race/` (TA-48): `pacing.ts` (pure, config `DEFAULT_RACE_PACING_CONFIG`): `bikeTarget` (FTP × a % band per race type, rounded to watts; half is 78–82%, so FTP 300 gives 234–246 W, `source` "from FTP 300"), `estimateRunThreshold` (fastest 20–60 min run within 90 days from whole-run averages, else `null`), `runTarget` (per-type factor, ±2% band), `fuelingPlan`, `swimNote`, `buildPacingPlan`, `formatPace`. `checklist.ts` `raceChecklist(raceType)`, `brief.ts` `raceBriefKind(race, today)`. The LLM never produces these numbers.
  - `reviews/`: `iso-week.ts` (`isoWeekKey` → `2026-W40`, `isoWeekRange`, `previousIsoWeek`) and `weekly-stats.ts` `computeWeeklyStats` (pure). Per sport: planned vs actual minutes with `compliancePct`, which is null (not 0) when nothing was planned; a week with no live non-rest session is `unplannedWeek`. Actual distance/TSS only (planned sessions carry neither). Key sessions hit/missed/pending by status. Z1-2 vs Z3+ minutes by avg HR (`hrIntensity` vs `Profile.lthr`, else unknown). CTL/ATL/TSB from before the week to its end, and wellness averages. The output is versioned JSON (`WEEKLY_STATS_VERSION`) with sorted lists and one decimal. `block-verdict.ts` `computeBlockVerdict(block, weeklyStats)` (volume achieved vs `targetWeeklyHours`, CTL delta vs `targetCtl`, compliance trend; weeks without stats count neither way) and `reprojectionSeed` (next block's planned hours × share achieved, capped one ramp step above).
  - Apps consume core from `dist/` (`main: ./dist/index.js`, TS project references). **Rebuild core after you change it** or the apps will see stale types.
- **packages/ai** (`@triathlon/ai`): The LLM adapter (`createLlmProvider`, Anthropic/mock, `withCallLog` writes `LlmCallLog`, config `AI_*`) and `context/`, the daily context builder. `buildDailyContext(deps, userId, date)` reads data through injected repos (`DailyContextDeps`; the worker's `coachDecisionRepo.listRecent` serves `decisions`). It computes trends in `trends.ts` (HRV 30d baseline, low below mean − 1 SD; compliance; TSB) and renders `src/prompts/daily-v1.md` (`{{placeholder}}`, strict; the build copies prompts to `dist/prompts`). The output must stay byte-deterministic: `date` is the only clock, every list is re-sorted, and numbers use fixed precision. `budget.ts` truncates oldest history, then decisions, then trend days; races, key sessions and upcoming sessions are never truncated. Prompt snapshots are `test/context/__snapshots__/*.md` (LF via `.gitattributes`, prettier-ignored). New prompt versions get a new file.
  - `chat/`: `runCoachChat(deps, input)`: system prompt `prompts/chat-system-v1.md` (persona, grounding, "I'm not a doctor" boundary) plus daily prompt and `prompts/chat-v1.md` → structured `{ reply, suggestion | null }` via `requestStructured` (shared one-repair call in `suggestion/parse.ts`) → `runGuardrails` when there are changes → one `CoachDecision` (`origin: 'chat'`). Plain answers write nothing; no rules-engine fallback in chat. `CoachDecisionSink.write` returns the id.
  - `suggestion/`: `runCoachSuggestion(deps, input)` runs daily prompt + `prompts/suggestion-v1.md` → `requestSuggestion` (structured output; exactly one repair call on invalid JSON/schema or `LlmContractError`, none when the LLM is unavailable) → `runGuardrails` → one `CoachDecisionSink.write`. `SessionDiff.sessionId` is `sessionKey` = `<date>/<slot>`. Guardrails are pure: integrity issues reject, per-change limits clamp (`DEFAULT_GUARDRAIL_CONFIG`: −50% max cut, no moves onto rest days, no intensity increases at readiness ≤2), and new `checkHardRules` violations on the patched plan reject. Reject, invalid twice and LLM down all fall back to `deterministicRecommendation` (rules engine only). Every run writes exactly one `CoachDecision`, even on internal errors; only the write itself may throw.
- **packages/integrations-icu** (`@triathlon/integrations-icu`): A typed intervals.icu REST client (`IcuClient`). It uses Basic auth `API_KEY:<key>`, retries with backoff on 429/5xx, throws `IcuAuthError` on 401 without retrying, and throws `IcuContractError` when zod validation fails. Tests inject `fetch` plus `baseDelayMs: 0` and use JSON fixtures in `test/fixtures/`. The worker uses it in `icu-connect.ts`: those handlers take injected deps (repo, keys, `createClient`) so tests don't need Prisma or the network.

## Conventions

- ESLint enforces `no-explicit-any`, `no-floating-promises`, `no-misused-promises`, `prefer-optional-chain`, and `require-array-sort-compare` (string arrays included). Use `void` only for fire-and-forget promises. Unused variables must start with `_`. Use the pino `logger` instead of `console.log`.
- **Code quality (SonarQube).** These rules also apply to `test/` and fakes, which ESLint ignores. Follow them when writing code: @CODE_QUALITY.md
- Prettier config is in `.prettierrc`. The commit message template is `.gitmessage` (`<type>: <subject>`, types like feat/fix/refactor; history also uses scopes, e.g. `feat(integrations-icu): ...`).
- Dates are handled as `yyyy-MM-dd` strings in the user's profile timezone (`date-fns-tz` `toZonedTime`).
